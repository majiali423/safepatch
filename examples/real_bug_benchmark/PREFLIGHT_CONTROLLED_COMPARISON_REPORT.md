# Preflight 受控小样本对照实验

实验日期：2026-07-30

## 一句话结论

开启 preflight 的最终结果为 11/14，关闭时为 9/14；但 28 次运行中没有出现
任何 preflight rejection，也没有出现任何 apply failure。因此这 2 次成功差异
**不能归因于 preflight**。本实验没有自然触发 preflight 的核心拦截机制，观察到的
差异来自不同模型采样产生的语义补丁差异。

## 实验设计

- 任务：7 个已通过环境验收的真实历史 Bug；
- 条件：preflight 开启与关闭；
- 重复：每题、每种条件各 2 次，共 28 个冻结槽位；
- 顺序：预先生成交错顺序，第二轮反转每题两种条件的先后顺序；
- 模型：`deepseek-v4-flash`，temperature `0.1`；
- 产品提交：`b455df2fd679f0c4a1e4ffe4894101a70ab3eb0f`；
- 调度哈希：`69c1cb4d76b5101b3b4954e93155cb2dd32ac28e148a88e43aede4c395412e4a`；
- 隐藏测试：Agent 完成后才注入，结果不反馈给修复循环；
- 重跑规则：模型、语义、预算或补丁失败均计入结果且不补跑；只有 API、Docker
  等环境失败可在原槽位恢复；本次环境失败为 0；
- 资源上限：60 分钟活动耗时或估算 0.25 美元，本次均未触发。

当前模型接口不提供可冻结的采样随机种子。两种条件的运行不能保证从同一初始补丁
开始，因此这是受控小样本对照，不是同随机序列的严格配对实验，也不构成因果证明。

|---|---:|---:|---|

| `tornado-11` | 2/2 | 2/2 | 两组稳定通过 |

开启组的三个失败包括两个隐藏测试失败和一次 `evidence_hard_violation`；关闭组五个
失败全部是公开测试通过后的隐藏测试失败。这些失败都不是补丁文本无法应用造成的。

## 为什么 11/14 对 9/14 不能算 preflight 提升

Preflight 的直接作用是：在审批和真实 apply 前，使用同一个精确匹配引擎检查补丁
是否能应用；如果上下文过期或不匹配，就拒绝补丁并要求重新读取与生成。

但本实验开启组的 13 个已提出补丁第一次就都可应用，关闭组的 14 个补丁也全部
成功 apply。换句话说，两组没有在 preflight 所控制的变量上产生行为分叉。tqdm、
Sanic 和 thefuck-16 的组间差异发生在业务语义上，而 preflight 本来就不负责证明
业务语义正确。

因此可以报告“冻结样本中观察到 11/14 与 9/14”，但不能写成“preflight 将成功率
提高 14.3 个百分点”，也不能声称 token 或耗时差异由 preflight 导致。

## 这次负结果的价值

实验推翻了一个过强的项目叙事：只在自然端到端样本中开关 preflight，不一定能
测到它的价值。下一次机制实验应使用冻结的 context-mismatch replay，或预先定义
会产生陈旧上下文的场景，直接衡量拒绝、重新读取、恢复和错误 repair attempt。
这类机制实验应与真实 Bug 的语义成功率分开报告，避免把“补丁能贴上”误写成
“Bug 修对了”。

公开证据位于 [`published/preflight-ablation-28-run/`](published/preflight-ablation-28-run/README.md)，
可在无 API、无 Docker 的情况下复算：

```bash
python examples/real_bug_benchmark/verify_preflight_ablation.py
```

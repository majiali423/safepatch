# 多文件真实 Bug 小样本模型评测

评测日期：2026-07-30

## 结论

初始基线使用 `deepseek-v4-flash` 对两个自然多文件任务各独立运行 2 次，公开、隐藏与最终通过均为 1/4。加入安全补丁恢复机制后，以相同任务资产、模型、温度、重复次数和 preflight 配置重新运行，三项通过率均为 3/4；`patch_not_applicable` 从 2/4 降为 0/4。

这是 4 次独立随机采样的小样本，不构成统计显著的因果证明。新轮没有出现 context mismatch，因此不能声称自动重定位或强制重读直接带来了两个新增成功；但新 `propose_edit` 被两次成功运行实际采用，且三个提出过补丁的运行首次 preflight 均成功。结果支持“这组复测中准确率与补丁可应用性同时改善”，不支持泛化到所有仓库或模型。

## 读取预算决策机制复测

加入“每次读取反馈剩余预算、剩余 3 次开始警告、预算归零后明确要求提交补丁或结束、连续两次越界读取提前终止”后，再以相同模型、温度、任务资产、重复次数和 preflight 配置运行 4 次。任务资产哈希仍为 `ac17134f...f48cea`，结果保存在 `results/deepseek_v4_flash_multifile_2x_read_budget_20260730/`。

| 指标 | 安全补丁恢复后 | 读取预算机制后 | 变化 |
|---|---:|---:|---:|
| 公开测试通过 | 3/4 | 3/4 | 不变 |
| 隐藏测试通过 | 3/4 | 2/4 | -1 次 |
| 最终通过 | 3/4 | 2/4 | -1 次 |
| Token | 1,509,623 | 1,216,544 | -293,079（-19.4%） |
| 模型调用 | 48 | 41 | -7（-14.6%） |

| 估算成本 | $0.02488115 | $0.02064353 | -$0.00423762（-17.0%） |
| `patch_not_applicable` | 0/4 | 0/4 | 不变 |

这轮两个 `thefuck-16` 均通过公开和隐藏测试，并都修改了 Bash、Zsh 两个产品文件。一个 `tornado-10` 在 12 次有效读取后连续提出两次越界读取：第一次收到明确警告，第二次立即以独立的 `READ_BUDGET_EXHAUSTED` 终止。与上一轮同类 Tornado 无补丁失败相比，该失败运行的模型调用从 20 降为 17，Token 从 722,919 降为 595,774，耗时从 155.870 秒降为 74.641 秒；说明失败路径更快、更明确，但不说明修复准确率提高。

另一个 `tornado-10` 提交了可应用补丁并通过公开测试，但隐藏测试发现它只在 `finish()` 后恢复了 `ui`，没有在连接关闭后清理 `ui`，因此最终失败。总体成功率从 3/4 降到 2/4，不能宣称准确率变好；考虑到每轮只有 4 个随机样本，这个差异也不能单独证明准确率变差。当前证据只支持：预算机制减少了本轮资源消耗，并把反复读取失败可靠地归类和提前终止；它没有解决 Tornado 的生命周期推理难题。

## 两级读取预算复测

该策略已标记为失败实验，不作为产品默认策略。产品恢复固定 12 次探索预算，并以结构化综合阶段取代自动储备。

为避免固定 12 次上限阻止模型读取最后一个关键生命周期区域，读取策略改为 12 次普通读取加 4 次定向 `read_file` 储备。储备只接受显式、未完全覆盖且不超过 120 行的范围；同时在系统提示和储备反馈中要求提交前检查创建、使用、正常清理和错误/关闭清理。相同模型、任务资产、温度、每题 2 次和 preflight 配置下，结果保存在 `results/deepseek_v4_flash_multifile_2x_two_tier_budget_20260730/`。

| 指标 | 固定 12 次预算 | 两级预算 | 变化 |
|---|---:|---:|---:|
| 公开测试通过 | 3/4 | 2/4 | -1 次 |
| 隐藏测试通过 | 2/4 | 2/4 | 不变 |
| 最终通过 | 2/4 | 2/4 | 不变 |
| Token | 1,216,544 | 1,378,228 | +161,684（+13.3%） |
| 模型调用 | 41 | 44 | +3（+7.3%） |
| 耗时 | 316.729 s | 302.074 s | -14.655 s（-4.6%） |
| 估算成本 | $0.02064353 | $0.02222398 | +$0.00158045（+7.7%） |

两个 `thefuck-16` 再次全部通过并各自修改 Bash、Zsh 两个产品文件。两个 `tornado-10` 均未提交补丁并以 `READ_BUDGET_EXHAUSTED` 结束。第一次 Tornado 用完 12 次普通读取和全部 4 次定向储备，随后才请求包含关闭路径的 `tornado/websocket.py:420-540`；第二次 Tornado 只成功使用 1 次储备，之后连续请求储备阶段不允许的搜索和一个 121 行范围，因而提前终止。

这轮说明定向储备能够在不恢复无限搜索的前提下增加调查空间，但模型未必会把储备用在关键路径，严格范围校验也可能把可纠正的一行边界错误与无效探索同样计为违规。最终成功率没有改善，Token、调用和成本反而上升，因此当前证据不支持把两级预算作为准确率优化成果。下一步应区分“可纠正的范围格式错误”和“继续宽泛探索”，并研究硬预算后的强制综合/候选补丁阶段，而不是继续简单增加读取次数。

Tornado 的成功运行只修改 `tornado/websocket.py`，通过覆盖 `finish()` 保存连接期 `ui`，并在 `on_close()` 后释放它。它通过了公开测试和模型不可见的生命周期隐藏测试，是功能正确的替代修复，但按“最终 diff 修改至少两个产品文件”的严格口径不算跨文件修复。这也说明该任务来自自然多文件参考修复，并不强制所有正确解都必须修改多个文件。

两次 `thefuck-16` 都实际修改 Bash 与 Zsh 两个产品实现并通过 2 个隐藏参数化用例，因此新轮有 2 次严格跨文件完成。第二次运行最初试图修改已有测试，被测试完整性策略拒绝；模型随后只修改产品代码并成功，安全门禁没有为提高分数而放宽。

失败的 Tornado 在达到 12 次读取预算后仍继续请求读取，最终达到分析步骤上限且没有提出补丁。新机制消除了本样本中的不可应用补丁，但没有解决复杂任务中的读取规划和停止决策。

## 实验设置

- 模型：`deepseek-v4-flash`
- 任务：`tornado-10`、`thefuck-16`
- 重复次数：每题 2 次，共 4 次独立运行
- preflight：开启
- 起点：每次重新检出任务冻结的 buggy commit
- 公开测试：模型可见，基线必须失败，修复后必须通过
- 隐藏测试：模型不可见，在 Agent 结束后才注入其修复工作副本
- 环境：每题使用固定 Docker 镜像和历史项目所需 Python 版本
- 计分：公开测试和隐藏测试都通过才计为 overall success

上表只统计初始可计分实验。修复隐藏测试链路前还执行过两轮各 4 次的无效试跑，它们不能用于模型成绩，但确实产生了 2,733,656 token、95 次调用、742.859 秒和约 $0.03964659 的调试支出。再计入初始正式实验与本次复测，整个多文件评测推进实际共调用 16 次，使用 5,995,867 token、202 次模型 API 调用、1,492.559 秒，估算总支出 $0.08409531。区分计分口径与实际支出，可以避免用无效结果评价模型，也避免隐瞒实验成本。

## 如何判断是否真的完成跨文件修复

跨文件判定只统计模型最终 diff 中的产品文件，不统计公开测试、隐藏测试或评测脚本。

`thefuck-16` 的成功运行同时修改 Bash 和 Zsh 的 alias 生成逻辑，把环境变量移动到 alias 的命令替换内部。公开测试通过，模型不可见的自定义 `fixit` alias 隐藏测试也以 `2 passed` 通过。因此该运行同时满足：修改两个产品文件、修复两个 shell 实现、公开行为正确、未见用例正确。

另一次 `thefuck-16` 没有产生可应用的最终补丁。preflight 连续 3 次发现补丁上下文与真实文件不匹配，在写入前拒绝了候选，因此不算跨文件修复。

`tornado-10` 的第一次运行读取了大量上下文，但最终没有提出补丁。第二次只修改 `tornado/websocket.py`：思路是连接建立后恢复 `ui`、关闭后清理 `ui`，但代码使用了未导入的 `ObjectDict`，导致 `NameError` 和 WebSocket 超时；公开与隐藏测试均失败。它既没有完成正确修复，也没有覆盖参考修复涉及的多文件设计。

## 隐藏测试链路校验

正式实验前发现并修复了评测器的两个路径问题：最初隐藏测试被施加到原始 source，而不是 Agent 的修复副本；改为修复副本后，Windows Git 又向上发现 SafePatch 主仓库，导致补丁没有落入 Docker 挂载目录。现在评测器通过 `GIT_CEILING_DIRECTORIES` 阻止父仓库发现，并有真实文件落点回归测试。

修复后先做了不调用模型的端到端验证：隐藏文件确实进入保存的 Agent 工作副本，Docker 能真实收集并运行它。`thefuck-16` 保存修复得到 2 个隐藏测试通过；一个公开测试已通过但关闭连接后未清理 `ui` 的 Tornado 保存修复，被隐藏测试准确判为失败。此前两轮路径有误的试跑不计入本报告任何成功率、token、耗时或成本统计。

## 可审计产物

初始与复测的原始 `metrics.json`、`summary.json`、`final.diff`、`trace.jsonl`、基线日志和隐藏测试日志分别保存在本地 `results/deepseek_v4_flash_multifile_2x_final_20260730/` 与 `results/deepseek_v4_flash_multifile_2x_recovery_20260730/`。`results/` 被 Git 忽略，避免提交大量临时会话或潜在运行信息；本报告是应提交的精简审计摘要。

## 下一步建议

下一步不应继续在这 4 次样本上宣称因果，而应补一个能确定触发“错位但唯一完整上下文”的合成或冻结任务，对自动重定位和强制重读做开关消融。对于本轮仍失败的 Tornado，应优先改善读取预算反馈与停止决策，而不是放宽补丁匹配或测试门禁。
